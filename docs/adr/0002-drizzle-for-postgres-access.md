# ADR-002: Drizzle ORM for PostgreSQL access and migrations

## Status

Accepted

## Context

Patchwork needs typed PostgreSQL access and a real migration workflow from
day one, usable from both `apps/api` and `apps/worker`, and testable against
a real PostgreSQL instance in CI. The current schema is intentionally
minimal (one table), but the access layer needs to scale to the product's
eventual data model without heavy rework.

Three options were assessed:

- **Prisma** — mature, widely used, generates a typed client from a schema
  DSL. Requires a code-generation step and a separate query-engine binary
  bundled at runtime, which adds build complexity and an extra moving part
  for a small team. Its schema language is also one more thing to learn on
  top of SQL, and migrations are managed through Prisma's own CLI/format.
- **Drizzle ORM + drizzle-kit** — typed schema defined in TypeScript that
  maps closely to SQL (not a separate DSL), no code-generation step, no
  bundled engine binary — it's a thin layer over `pg`/`postgres`. Migrations
  are plain `.sql` files generated by `drizzle-kit`, which are easy to read,
  review, and apply with a small migrator function. Query API stays close to
  SQL, which keeps the abstraction overhead low.
- **Direct SQL (hand-written queries via `pg`, hand-rolled migration
  runner)** — lowest abstraction, but reinventing migration tracking and
  losing compile-time type safety on queries is real risk for a product
  meant to be maintained long-term, for marginal benefit over Drizzle.

## Decision

Use **Drizzle ORM** with **drizzle-kit** for schema definition and migration
generation, and `pg` (`node-postgres`) as the underlying driver.

## Consequences

- Typed queries and typed schema (`packages/db/src/schema.ts`) without a
  code-generation step blocking iteration.
- Migrations are plain SQL files under `packages/db/migrations/`, applied via
  a small script (`packages/db/src/migrate.ts`) using Drizzle's built-in
  Node-Postgres migrator. `pnpm db:migrate` runs them.
- Integration tests can run real migrations against a real PostgreSQL
  instance cheaply (no engine binary to download/start).
- Low abstraction overhead: the query builder reads close to SQL, which
  matters for a modular monolith where multiple future modules (impact
  analysis, patch generation, verification) will each need direct, legible
  data access without fighting an ORM.
- Trade-off: less "magic" than Prisma (no auto-generated admin UI, less
  mature ecosystem of examples), considered an acceptable cost for the
  simplicity and control gained.
